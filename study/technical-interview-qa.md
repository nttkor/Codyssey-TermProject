### 1. 우리의 서비스는 어떤 서비스인가?
- **서비스 정의**: AskMate는 **사용자 맞춤형 실시간 웹 기반 AI 대화(Chatbot) 서비스**입니다.
- **핵심 기능 및 사용자 가치**:
  1. **개인화된 보안 계정**: 회원가입, 로그인/로그아웃, 세션 쿠키 기반의 독립된 개인 대화 공간을 제공합니다.
  2. **문맥 인지 다중 턴(Multi-turn Context-aware) 대화**: 직전의 단발성 질의응답에 그치지 않고, 데이터베이스에서 사용자의 **최근 5쌍(총 10개 턴)의 대화 기록**을 조회하여 외부 LLM(OpenAI 호환 API)에 문맥으로 주입함으로써 연속성 있는 자연스러운 상담이 가능합니다.
  3. **대화 이력 영구 보존 및 조회**: 과거 질의응답 내역을 SQLite DB에 안전하게 기록하고, 전용 히스토리 화면(`/history`)을 통해 시간순으로 열람할 수 있습니다.
  4. **단일 페이지(SPA) 스타일의 동적 UI**: 전체 페이지 새로고침 없이 비동기(Fetch API)로 질문을 전송하고 화면 일부(DOM)만 동적으로 갱신하여 쾌적한 사용자 경험을 제공합니다.

### 3. 현재 코드구조에서 사용자가 많아졌을 때 감당할 수 있을까? 확장 방안

#### 현재 아키텍처의 병목 한계
1. **SQLite의 단일 쓰기 잠금 (File-level Write Lock)**:
   - SQLite는 읽기는 병렬로 가능하지만, 쓰기(INSERT/UPDATE) 시에는 데이터베이스 파일 전체에 락이 걸립니다. 동시 접속자 수천 명이 동시에 질문을 던져 DB에 커밋할 경우 `sqlite3.OperationalError: database is locked`가 발생합니다.
2. **단일 Uvicorn 프로세스 및 로컬 세션**:
   - 현재는 단일 인스턴스 단일 프로세스로 동작하여 멀티코어 CPU의 병렬 처리 능력을 온전히 활용하지 못하며, 서버 장애 시 단일 장애점(SPOF)이 됩니다.
3. **LLM 응답 대기 커넥션 점유**:
   - 비동기 처리라 하더라도 동시 접속자가 급증하면 수천 개의 HTTP 소켓과 메모리가 AI 응답 대기 상태로 유지되어 OS 파일 디스크립터(FD) 한계에 도달할 수 있습니다.

#### 향후 엔터프라이즈 확장 로드맵 (Scale-up & Scale-out)
1. **관리형 RDBMS 전환 (PostgreSQL / MySQL)**:
   - 이미 SQLAlchemy ORM으로 모델과 DAL이 추상화되어 있으므로, `DATABASE_URL`을 분리된 PostgreSQL 클러스터로 교체하고 커넥션 풀(QueuePool) 크기를 확장합니다.
   - Master-Slave 구조(읽기 복제본)를 분리하여 대화 이력 조회(`history.py`)는 Slave로 분산합니다.
2. **세션 저장소 분리 (Redis Session Cluster)**:
   - 다중 백엔드 컨테이너 간 세션 상태를 공유할 수 있도록 분산 인메모리 캐시인 Redis에 세션을 저장합니다.
3. **로드 밸런서 및 컨테이너 오케스트레이션 (Nginx + Docker Swarm / Kubernetes)**:
   - Nginx 또는 ALB 뒤에 여러 대의 백엔드 워커 컨테이너를 배치하고 트래픽을 라운드로빈/Least Connections로 분산합니다.
4. **비동기 작업 큐 및 스트리밍 (Celery / RabbitMQ / Redis Streams + SSE)**:
   - AI 답변 생성을 즉시 처리하지 않고 메시지 큐에 넣은 뒤 백그라운드 워커가 처리하도록 분리하고, 클라이언트에는 Server-Sent Events(SSE)로 생성되는 토큰을 실시간 스트리밍 반환합니다.

### 4. 외부 서비스(AI API) 장애 시 동작 원리 및 429 에러 처리

#### 현재 장애 대응 동작 원리
- `backend/app/llm_connect.py`에서 비동기 호출을 수행하며, 외부 장애를 철저히 캡슐화합니다:
  - **시간 초과 (`APITimeoutError`)**: `AITimeoutError` 발생 ➔ `llm.py`에서 `HTTP 504 Gateway Timeout` ("AI 응답이 지연되어 답변을 받지 못했습니다. 잠시 후 다시 시도해 주세요.")으로 매핑.
  - **제공자 서버 다운 / 5xx 오류 (`OpenAIError`, `JSONDecodeError`)**: `AIServiceError` 발생 ➔ `llm.py`에서 `HTTP 502 Bad Gateway` ("AI 서비스에 연결하지 못했습니다. 잠시 후 다시 시도해 주세요.")로 매핑.
  - **🛡️ DB 원자적 미저장 원칙**: AI 응답이 실패하거나 비정상(빈 문자열, choices 누락)인 경우 **데이터베이스에 질문과 답변을 일체 저장하지 않습니다.**
  - **프론트엔드 복구**: `chat.js`가 502/504 상태 코드를 수신하면 실패한 질문을 `lastFailedQuestion`에 캐싱하고, 화면에 노란색 에러 배너와 **[다시 시도]** 버튼을 노출하여 사용자가 타이핑했던 질문을 즉시 원클릭 재전송할 수 있도록 돕습니다.

#### 429 (Too Many Requests / Rate Limit) 에러 처리 전략
1. **단기 지수 백오프 (Exponential Backoff with Jitter)**:
   - `openai.RateLimitError`를 감지하여 응답 헤더의 `Retry-After` 초만큼 대기하거나, 1~2초 간격으로 지수 백오프 기반 재시도를 내부 1회 시도합니다.
2. **사용자 친화적 안내 메시지 분기**:
   - `HTTP 429` 상태 코드 수신 시 "현재 AI 서비스 요청량이 많아 일시적으로 처리가 지연되고 있습니다. 약 10초 후 다시 시도해 주세요."와 같이 대기 시간을 포함한 명확한 안내를 반환합니다.
3. **서비스 내부 Rate Limiting 도입 (`slowapi` / Redis Token Bucket)**:
   - 악의적인 단일 유저가 API를 난사하여 외부 AI 서비스의 전역 토큰/요청 쿼터가 소진되는 것을 막기 위해, 백엔드 엔드포인트에 유저당 1분당 최대 10회 등의 속도 제한을 선제 적용합니다.

### 5. 서비스 장애 시 로그를 보고 복구할 수 있을까?

- **복구 가능한 영역**:
  1. **장애 원인 추적**:
     - `request_received user_id=... path=...`를 통해 어떤 사용자가 장애를 겪었는지 파악 가능합니다.
     - `ai_call_failure error_type=... elapsed=...`를 통해 외부 게이트웨이의 문제인지, 타임아웃인지, 페이로드 파싱 실패인지 즉시 판별 가능합니다.
     - `db_save_failure`, `db_read_failure` 로그를 통해 데이터베이스 I/O 병목 여부를 확인할 수 있습니다.
  2. **데이터 일관성 보장**:
     - SQLAlchemy 세션 롤백(`db.rollback()`) 정책이 적용되어 있어, 장애 발생 시 불완전한 대화 레코드가 생성되지 않으므로 DB 정합성 복구 작업이 불필요합니다.
- **복구의 한계점 및 보완점**:
  - **본문 미저장 보안 정책**: 개인정보 보호 및 보안 규정(API 키 및 질문 본문 로그 노출 금지)에 따라 질문/답변 텍스트를 로그에 남기지 않으므로, 유저가 입력했던 질문 내용을 로그 파일에서 직접 복원할 수는 없습니다. (대신 사용자의 브라우저 클라이언트 메모리 `lastFailedQuestion`에서 복원 재전송 지원).
  - **분산 환경 대비**: 향후 다중 서버 배포 시 요청 추적을 위한 고유 트랜잭션 ID(`trace_id` / `request_id`)를 로그 포맷에 주입(Correlation ID)해야 여러 컨테이너 로그를 하나로 꿰어 복구할 수 있습니다.

### 6. 로그를 어디에, 어떻게 저장해야 할까?

#### 현재 구현 상태
- `backend/app/logger.py`에서 `RotatingFileHandler`를 사용하여 컨테이너 내부 `data/app.log` 파일에 저장합니다.
- 파일당 최대 5MB, 최대 3개(총 15MB)까지 백업 회전(Rotation)하여 디스크 고갈을 방어하며, 표준 출력(stdout)으로도 동시 출력합니다.

#### 프로덕션(운영 환경)의 바람직한 아키텍처
1. **12-Factor App 로깅 원칙 준수**:
   - 컨테이너 내부 파일 저장을 지양하고, **모든 로그를 표준 출력(`stdout`/`stderr`) 스트림으로 배출**합니다.
2. **로그 수집 에이전트 (Log Shipper)**:
   - 호스트 또는 사이드카 컨테이너로 실행되는 Fluentbit, Vector, Promtail이 Docker 컨테이너의 표준 출력을 비동기로 스크랩합니다.
3. **중앙 집중식 로그 분석 플랫폼 (Centralized Logging)**:
   - 오픈소스: **Grafana Loki** (경량, 비용 효율적) 또는 **Elasticsearch + Kibana (ELK)**
   - 클라우드 네이티브: **AWS CloudWatch**, **OCI Logging Service**, **GCP Cloud Logging**
4. **민감 정보 마스킹 및 수명주기(Retention) 관리**:
   - 비밀번호, API 키, 주민번호/전화번호 등 개인식별정보(PII)는 필터를 통해 마스킹.
   - 일반 접속 로그 30일 보관, 보안 감사 로그 1년 보관 후 콜드 스토리지(S3, OCI Object Storage) 자동 아카이빙/파기 정책 수립.

### 7. 인증과 인가를 어떤 식으로 처리하는가?

#### 인증 (Authentication - "당신은 누구인가?")
1. **Argon2id 비밀번호 검증**: 로그인 시 사용자 입력 비밀번호를 DB의 `password_hash`와 상수 시간 비교(`verify_password`)하여 검증합니다.
2. **세션 쿠키 발급**: 인증 성공 시 Starlette `SessionMiddleware`를 통해 HMAC 서명된 `askmate_session` 쿠키를 브라우저에 발급합니다.
3. **세션 고정(Session Fixation) 방어**: 로그인 직후 기존 세션을 비우고(`request.session.clear()`) 새로운 사용자 ID를 부여합니다.

#### 인가 (Authorization - "당신은 이 자원에 접근할 권한이 있는가?")
1. **계층형 FastAPI 의존성 주입 (`Depends`)**:
   - `get_session_user`: 쿠키에서 `user_id`를 확인하고 DB 유저 객체를 반환하며, 비로그인 시 `None`을 반환합니다. (페이지 라우터에서 비인가 접근 시 `/login`으로 303 Redirect)
   - `get_current_user`: API 엔드포인트(`/api/chat`, `/api/me`, `/api/me/chats`)에 적용되며, `user is None`일 경우 즉시 `HTTP 401 Unauthorized`를 발생시켜 접근을 차단합니다.
2. **데이터 격리 (Object-Level Authorization)**:
   - 대화 내역 조회 시 항상 세션에서 검증된 `user.id`를 기준으로 쿼리(`Chat.user_id == current_user.id`)하여 타인의 대화 기록 접근을 원천 차단합니다.
3. **CSRF 인가 가드**:
   - 모든 상태 변경(POST) API에 `require_csrf_header` 의존성을 적용하여 `X-Requested-With: XMLHttpRequest` 헤더가 없는 요청을 `403 Forbidden`으로 거부합니다.

### 9. 외부 서비스에서 응답을 안 주면 무한정 기다려야 할까?

- **결론: 절대로 무한정 기다려서는 안 됩니다.** (안티패턴)
- **무한 대기 시 발생하는 치명적 문제**:
  - 외부 서버가 먹통이 되었을 때 클라이언트와 백엔드 서버 간의 TCP 소켓 연결이 열린 채 유지됩니다.
  - 요청이 쌓이면 백엔드 서버의 커넥션 풀과 파일 디스크립터가 고갈되어 서버 전체가 응답 불가 상태(Resource Starvation)에 빠집니다.
- **AskMate의 엄격한 방어 구현**:
  1. **유한한 타임아웃 검증 (`AI_TIMEOUT`)**:
     - `config.py`와 `config_validation.py`에서 `math.isfinite() and > 0` 검증을 통과한 유한한 양수(기본 30초)만 허용합니다. (`nan`, `inf`, `-1` 등 무한 대기 유발 값 원천 차단)
  2. **SDK 타임아웃 주입**:
     - `AsyncOpenAI(timeout=AI_TIMEOUT)`으로 등록되어 30초 동안 응답이 없으면 즉시 `APITimeoutError`를 발생시키고 소켓을 끊습니다.
  3. **HTTP 504 반환 및 자동 재시도 차단**:
     - `max_retries=0`으로 설정하여 보이지 않는 곳에서 대기 시간이 60초, 90초로 곱절 늘어나는 현상을 막고, 30초 시점에 504 Gateway Timeout으로 깔끔하게 실패 처리합니다.

### 10. 오류가 났을 경우 사용자에게 어떻게 안내해야 할까?

3. **화면 복구 및 행동 유도 (Actionable UX)**:

### 11. await 키워드의 의미, 비동기 동작 원리 및 이벤트 루프

#### `await` 키워드의 본질적인 의미
- 비동기 코루틴(Coroutine) 함수 안에서 호출되며, **"이 비동기 I/O 작업이 완료될 때까지 현재 함수의 실행을 잠시 중단(Suspend)하고, CPU 제어권(Control)을 이벤트 루프에 양보(Yield)하겠다"**는 선언입니다.
- 스레드 자체를 블로킹(Sleep)하는 것이 아니라, 함수 실행 문맥만 잠시 멈추고 다른 작업이 돌 수 있게 스케줄러에 통제권을 넘깁니다.

#### 비동기 처리 동작 원리와 이벤트 루프 (Event Loop)
1. **단일 스레드 기반 동시성 (Single-threaded Concurrency)**:
   - FastAPI/Uvicorn은 메인 스레드에 1개의 이벤트 루프를 두고 수많은 태스크(Task)를 비동기로 스케줄링합니다.
2. **동작 시나리오**:
   - 유저 A가 `/api/chat`을 호출하면 `await llm_connect.generate_answer(...)`를 만납니다.
   - 외부 AI 게이트웨이로 패킷을 쏘고 응답 소켓을 열어둔 채, 유저 A의 태스크는 대기 큐로 들어갑니다.
   - 이벤트 루프는 쉬지 않고 그 사이에 들어온 유저 B의 로그인 요청, 유저 C의 정적 파일 요청, 헬스체크(`/health`) 요청을 막힘없이 처리합니다.
   - OS 커널의 I/O 멀티플렉서(`epoll` / `kqueue`)가 AI 응답 패킷 도착을 감지하면 이벤트 루프에 알리고, 이벤트 루프는 유저 A의 태스크를 깨워(Resume) `await` 다음 코드(DB 저장 등)를 실행합니다.
3. **주의점: 동기 I/O 블로킹 차단 (`run_in_threadpool`)**:
   - SQLAlchemy의 SQLite 디스크 I/O는 동기식(blocking) 코드입니다. 만약 이벤트 루프 안에서 동기 I/O를 직접 실행하면 이벤트 루프 전체가 멈춰버립니다.
   - 따라서 AskMate는 `run_in_threadpool(get_recent_chats_by_user, ...)`과 같이 동기 DB 작업을 별도의 스레드 풀로 넘겨 이벤트 루프의 무중단을 보장합니다.

### 13. 같은 사용자가 동시에 여러 기기에서 접속하면 어떻게 되는가?

- **현재 아키텍처 동작**:
  - AskMate는 클라이언트 쿠키에 서명된 세션을 보관하는 구조(`askmate_session`)를 사용합니다.
  - 따라서 사용자가 스마트폰(기기 A)과 노트북(기기 B)에서 동일한 아이디로 로그인하면, 두 브라우저 모두 유효한 세션 쿠키를 갖게 되므로 **동시 접속 및 양쪽 기기에서의 자유로운 대화가 완벽히 가능합니다.**
- **대화 문맥 공유**:
  - DB의 `chats` 테이블은 `user_id`를 외래키로 저장합니다.
  - 기기 A에서 질문을 남긴 후 기기 B에서 새 질문을 보내면, 백엔드는 동일한 `user.id`의 최신 5쌍 대화를 DB에서 긁어오므로 **기기 A에서 나눈 대화 내용이 기기 B의 AI 문맥에도 자연스럽게 반영**됩니다.
- **동시 로그인 제한(중복 로그인 차단)이 필요하다면?**:
  - `users` 테이블에 `current_session_token` 컬럼을 추가하고, 로그인 시마다 난수를 생성하여 세션 쿠키와 DB 양쪽에 기록합니다.
  - 요청이 올 때마다 쿠키의 토큰과 DB의 토큰을 비교하여, 다른 기기에서 새로 로그인하면 이전 기기의 세션이 자동으로 무효화되도록 구현할 수 있습니다.

### 14. 악성 사용자 입력에 대해 어떻게 처리하는가?

AskMate는 5단계 심층 방어(Defense in Depth) 체계를 갖추고 있습니다:

1. **SQL Injection 방어**:
   - 문자열 결합(`"SELECT ... WHERE id = " + input`)을 절대 사용하지 않고, SQLAlchemy ORM의 파라미터 바인딩(`select(Chat).where(Chat.user_id == user_id)`)을 통해 사용자 입력이 SQL 구문으로 실행되는 것을 100% 원천 차단합니다.
2. **XSS (Cross-Site Scripting) 방어**:
   - 악의적인 사용자가 `<script>alert(document.cookie)</script>`나 `<img src=x onerror=...>` 형태의 스크립트를 질문으로 보내거나 AI 답변으로 유도하더라도, 프론트엔드(`chat.js`, `common.js`, `history.js`)에서 화면에 렌더링할 때 `innerHTML`을 일체 배제하고 **`textContent` 프로퍼티만을 사용**하여 브라우저가 순수 문자열(Plain Text)로만 해석하도록 강제합니다.
3. **Pydantic v2 스키마 기반 엄격한 서버 유효성 검증**:
   - `ChatRequest` 스키마에서 `StringConstraints(strip_whitespace=True, min_length=1, max_length=1000)`를 적용하여 공백 문자열 제거, 1자 미만 차단, 1000자 초과 입력을 사전에 거부(422)합니다.
4. **한글 IME 조합 오작동 방어**:
   - 한글 입력 조합 중 Enter 입력으로 인한 글자 깨짐 및 중복 전송을 `isComposing` 플래그로 차단합니다.
5. **민감정보 로그 유출 방지**:
   - 전역 예외 처리기(`RequestValidationError`)에서 비밀번호 등 민감 필드 값을 마스킹하여 로그에 남지 않도록 통제합니다.

### 15. 쿠키를 위변조하면 어떻게 되는가?

- **보안 메커니즘**:
  - `SessionMiddleware`는 서버 측의 강력한 대칭키(`SESSION_SECRET_KEY`)를 사용하여 쿠키 데이터를 암호화 서명(HMAC)합니다.
- **위변조 시 시스템의 반응**:
  1. 공격자가 브라우저 개발자 도구(F12)에서 쿠키 문자열을 임의로 조작하거나, 다른 사용자의 `user_id`를 주입하여 위조를 시도합니다.
  2. 서버에 요청이 도달하면 `SessionMiddleware`가 쿠키의 암호화 서명 검증을 시도합니다.
  3. 서명이 일치하지 않으므로 미들웨어는 위변조된 쿠키를 즉각 **폐기하고 빈 세션(`request.session = {}`)으로 초기화**합니다.
  4. 그 결과 `auth.py`의 `get_session_user`는 `user_id`를 찾지 못해 `None`을 반환합니다.
  5. API 엔드포인트는 `HTTP 401 Unauthorized`를 뱉고, HTML 페이지는 `/login`으로 강제 리다이렉트되어 시스템에 침투할 수 없습니다.
  6. **서명의 결합:** 서버가 로그인 성공 시 브라우저에 쿠키를 줄 때, 단순히 $user\_id=1$ 같은 데이터만 덜렁 보내는 것이 아닙니다. 서버 혼자만 알고 있는 절대적인 비밀번호인 $SESSION\_SECRET\_KEY$ 를 사용하여 복잡한 암호학적 도장(서명)을 찍은 뒤, `데이터 + 서명`을 한 덩어리로 묶어서 보냅니다.
  7. **위조 시 서명 불일치 발생:** 만약 공격자가 개발자 도구에서 $user\_id$ 를 $1$ 에서 $2$ 로 몰래 바꾼다고 가정해 보겠습니다. 글자는 쉽게 바꿀 수 있지만, 쿠키에 함께 붙어있는 '서명'은 원래 데이터인 $1$ 에 맞춰진 예전 서명 그대로입니다. 서버의 $SESSION\_SECRET\_KEY$ 를 모르면 $user\_id=2$ 에 맞는 올바른 새 서명을 절대로 만들어낼 수 없습니다.
  8. **서버의 철저한 재검증:** 위조된 쿠키가 서버에 도착하면, $SessionMiddleware$ 가 쿠키 안의 데이터를 꺼내어 자신의 $SESSION\_SECRET\_KEY$ 로 서명을 다시 계산해 봅니다. 데이터가 조작되었으므로 서버가 방금 계산한 서명과 쿠키에 묻어온 서명이 완전히 다르게 나옵니다.
  9. 따라서 문서에 적힌 것처럼 서버는 서명이 일치하지 않는 것을 확인하는 즉시 "이 쿠키는 누군가 임의로 조작했다!"고 판단하고, 해당 쿠키를 폐기한 뒤 빈 세션으로 초기화해 공격자의 침투를 완벽하게 차단합니다.

### 16. 클라이언트의 네트워크가 느리거나 끊기면 어떻게 처리되는가?

#### 프론트엔드 네트워크 장애 복구 (`common.js` & `chat.js`)
1. **`fetch()` 실패 안전 포착**:
   - 사용자의 와이파이가 끊기거나 터널 진입 등으로 오프라인 상태가 되면 `fetch()`는 네트워크 에러를 던집니다.
   - `common.js`의 `apiRequest` 함수가 `try-catch` 블록으로 이를 감싸서 `status: 0`, `data: { detail: "네트워크 연결에 실패했습니다." }`로 정규화하여 반환합니다.
2. **UI 상태 복구 및 재시도 UX**:
   - `chat.js`는 네트워크 단절 시에도 화면이 멈추지 않고 에러 배너를 노출합니다.
   - 비활성화되었던 전송 버튼과 텍스트 입력창을 다시 활성화(`disabled = false`)하고, 실패한 질문을 `lastFailedQuestion`에 캐싱하여 네트워크가 연결된 후 [다시 시도] 버튼 클릭 한 번으로 재전송할 수 있게 합니다.
3. 자바스크립트에서 `fetch()` 요청이 에러가 아닌 '성공'이라고 판별하는 기준은 **HTTP 상태 코드가 200번대(200~299)인지 확인하는 것**입니다.

   가장 대표적인 성공 코드는 정상 처리를 의미하는 **200 (OK)** 또는 데이터가 성공적으로 생성되었음을 뜻하는 201 (Created)입니다.

   `fetch()`를 사용할 때 이를 코드에서 쉽게 구분할 수 있도록 브라우저는 `response.ok`라는 아주 편리한 속성을 제공합니다. 이를 기준으로 세 가지 상황을 명확하게 나눌 수 있습니다.

   * **성공 (정상 응답):**
   서버와 통신이 잘 되었고 결과도 정상인 경우입니다. 상태 코드가 200~299 사이로 들어오며, `response.ok` 값이 `true`가 됩니다. 이때 백엔드가 보내준 진짜 데이터를 꺼내서 화면에 보여줍니다.
   * **HTTP 에러 (404, 500, 401 등):**
   서버에 연결은 성공했지만, 서버 측에서 문제가 있다고 응답한 경우입니다(예: 페이지 없음, 서버 내부 오류, 권한 없음). 이때는 `response.ok` 값이 `false`가 됩니다. 코드는 에러임을 인지하고 서버가 보내준 에러 메시지를 화면에 띄웁니다.
   * **네트워크 완전 단절 (상태 코드 0):**
   와이파이가 끊기는 등 아예 서버로 요청이 출발조차 하지 못해 `fetch()` 자체가 뻗어버린 경우입니다. 앞서 말씀드린 대로 자바스크립트의 `catch` 블록에서 이 뻗어버린 에러를 주워 담아, 다른 HTTP 에러들과 구분하기 위해 상태 코드를 강제로 **0**으로 세팅하여 반환합니다.

   결과적으로 개발자는 `response.ok`가 `true`인지 확인하여 성공을 판별하고, `false`이거나 `catch`로 빠졌을 때 상태 코드 번호(0인지, 400번대인지, 500번대인지)를 보고 어떤 종류의 에러인지 세부적으로 파악하게 됩니다.
   
#### 백엔드 네트워크 유실 대응
- 클라이언트가 요청 도중 접속을 끊으면 Uvicorn/ASGI 레벨에서 클라이언트 연결 해제(Client Disconnect)를 감지하여 불필요한 백엔드 연산을 중단하고 소켓을 안전하게 회수합니다.

### 17. 우리 DB, BE가 죽게 된다면 어떤 경우이며 어떻게 처리되는가?

#### 서버 및 DB가 다운될 수 있는 위험 요인
1. **OOM (Out Of Memory)**:
   - 트래픽 폭주 또는 대량의 메모리 누수로 컨테이너 메모리 제한(RAM Limit)을 초과할 경우 리눅스 OS 커널의 OOM Killer가 Uvicorn 프로세스를 강제 종료(SIGKILL)합니다.
2. **호스트 디스크 풀 (Disk Full)**:
   - 회전하지 않는 로그 파일이나 SQLite DB 파일이 비대해져 호스트 디스크 여유 공간이 0이 되면 모든 DB 쓰기 작업이 실패하며 프로세스가 다운될 수 있습니다.
3. **처리되지 않은 예외(Unhandled Crash)**:
   - 기동 시 필수 환경변수(`SESSION_SECRET_KEY`, `AI_API_KEY` 등) 누락이나 문법 오류로 인한 앱 시작 실패.

#### 현재 구축된 복구 및 방어 체계
1. **Docker 컨테이너 자동 재시작 정책 (`restart: unless-stopped`)**:
   - 프로세스가 예상치 못하게 죽더라도 호스트의 Docker 데몬이 컨테이너의 비정상 종료를 감지하고 수 초 내로 프로세스를 즉각 자동 재기동합니다.
2. **FastAPI Lifespan 생명주기 관리**:
   - 서버 기동 시 DB 초기화(`init_db`)와 테이블 무결성을 검증하고, 종료 시그널(SIGTERM) 수신 시 진행 중인 DB 세션과 엔진을 안전하게 정리(Graceful Shutdown)합니다.
3. **로그 용량 제한 회전 (`RotatingFileHandler`)**:
   - 로그 파일 용량을 5MB x 3개(최대 15MB)로 제한하여 디스크 풀로 인한 다운을 원천 차단합니다.
4. **헬스체크 엔드포인트 (`GET /health`)**:
   - 외부 모니터링 시스템이나 로드밸런서가 서버의 생존 여부와 DB 접근 가능 여부를 주기적으로 감시합니다.

### 18. 코드가 다음 작업자 혹은 동료가 이해하기 쉬운가?

- **높은 가독성과 유지보수성의 근거**:
  1. **모든 소스코드(35개 파일 전수)에 상세 Docstring 및 주석 완비**:
     - 파일마다 상단에 [파일 개요], [보안 고려사항], [역할 분담 및 협업 구조] 명시.
     - 모든 함수와 클래스에 Google Style Docstring(Args, Returns, Raises, 기술 원리) 작성 완료.

     - 라우터(`pages.py`, `account.py`, `llm.py`, `history.py`)
     - 데이터 접근 계층 DAL(`account_db.py`, `chat_db.py`)
     - 비즈니스 및 외부 연동 계층(`llm_connect.py`, `security.py`, `auth.py`)
     - 데이터 모델(`models/user.py`, `models/chat.py`)
     - 공통 유틸리티(`utils/datetime_utils.py`, `utils/db_utils.py`)
     - 각 계층의 책임이 명확하여 새로운 기능 추가 시 수정 대상 파일이 명확합니다.
  3. **엄격한 정적 타입 힌트 (Type Hints)**:
     - `typing.Annotated`, Pydantic 스키마를 철저히 사용하여 IDE 상에서 코드 탐색과 자동완성이 원활하며 타입 에러를 사전에 방지합니다.
  4. **풍부한 자동화 테스트 슈트**:
     - 백엔드 pytest 122개 테스트 및 프론트엔드 단위 테스트가 통과 상태로 유지되어, 동료가 코드를 리팩토링할 때 회귀 버그 발생 여부를 즉각 검증할 수 있습니다.
